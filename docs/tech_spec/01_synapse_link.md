## 3. 연결 (`[Vishamos-Net-…]`)

### 3.1 연결 상태 (`[Vishamos-Net-Status]`)

| 상태 | 뜻 | 다음 상태 |
|---|---|---|
| 연결 안 됨 | 시작 직후, 끊긴 뒤 재접속 대기 | 재접속 시각이 되면 → 접속 중 |
| 접속 중 | WebSocket 접속 시도 | 성공 → 등록 대기 / 실패 → 연결 안 됨 |
| 등록 대기 | 접속 성공, `client.register`를 보내고 응답 대기 | `client.registered` 수신 → 연결됨 / 끊김 → 연결 안 됨 |
| 연결됨 | 데이터 수신 | 끊김 → 연결 안 됨 |

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.1a | 상태는 위 4개로 닫는다. 상태가 바뀔 때마다 로그를 한 줄 남긴다(`이전 → 다음`, 끊김이면 종료 코드·이유). | 확정(사용자 답변) | `[Vishamos-Net-Status]`. 표시는 로그만, 화면 표시는 VishasController |
| 3.1b | 상태를 화면에 표시하지 않는다. | 확정(사용자 답변) | `[Vishamos-Net-Status]`, CLAUDE.md 안전 규칙 1 |
| 3.1c | 다른 스크립트가 현재 상태를 읽을 수 있게 한다(나중에 Controller로 보낼 때 씀). | AI 제안 | 상태를 바깥에 알릴 경로가 하나는 있어야 함 |

### 3.2 접속·등록 (`[Vishamos-Net-Connect]`, `[Vishamos-Net-Register]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.2a | 실행하면 자동으로 접속한다. 주소: `ws://<ServerHost>:<ServerPort>` | 확정 | `[Vishamos-Net-Connect]`, Synapse §1 |
| 3.2b | 접속 직후 기다리지 않고 텍스트로 `{"to":0,"from":11,"type":"client.register","data":""}`를 보낸다. 서버가 먼저 보내는 메시지는 없다(옛 `[0,0]` 대기 제거). | 확정 | `[Vishamos-Net-Register]`, Synapse §3, §9 |
| 3.2c | `client.registered`를 받기 전에 온 바이너리는 버린다. | 해석 | `[Vishamos-Net-Register]` "받은 뒤부터 처리". 서버도 등록 전에는 전달하지 않으므로 실제로는 오지 않음 |
| 3.2d | 등록 응답을 기다리는 클라이언트 쪽 시간 제한은 두지 않는다. 등록이 안 되면 서버가 30초 뒤 끊고(1008), 3.3에 따라 다시 접속한다. | 해석 | Synapse §3. 서버 시간 제한으로 충분 |
| 3.2e | 접속 시도 자체의 시간 제한: 5초 | AI 제안 | 서버 PC가 꺼져 있으면 `ConnectAsync`가 OS 기본 시간(수십 초)까지 걸려 재접속 3초 간격이 의미 없어짐 |

### 3.3 재접속 (`[Vishamos-Net-Reconnect]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.3a | 끊기면 정상 종료·비정상 종료(`Closed`·`Aborted`·예외) 모두 `ReconnectSeconds`(기본 3초) 뒤 새 소켓으로 다시 접속하고 다시 등록한다. 접속 실패도 같다. | 확정(사용자 답변) | `[Vishamos-Net-Reconnect]` |
| 3.3b | 재접속 시도는 한 번에 하나만 돈다(중복 루프 금지). | 확정 | `[Vishamos-Net-Reconnect]`. 옛 코드는 코루틴이 2개 생겨 연결이 10초마다 끊겼음(§8) |
| 3.3c | 끊긴 소켓은 정리(Dispose)한 뒤 새 소켓을 만든다. | 해석 | `ClientWebSocket`은 재사용할 수 없음 |

### 3.4 수신 (`[Vishamos-Net-Receive]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.4a | 연결 중에는 수신 대기(`ReceiveAsync`)를 항상 걸어 둔다. `ClientWebSocket`은 수신 대기 중일 때만 서버 ping에 pong을 자동으로 보낸다. | 확정 | `[Vishamos-Net-Receive]`, Synapse §7 |
| 3.4b | 한 메시지는 `EndOfMessage`가 올 때까지 이어 붙여 하나로 처리한다. | 확정 | `[Vishamos-Net-Receive]` |
| 3.4c | 이어 붙인 길이가 64KB를 넘으면 그 메시지를 버리고 경고 로그를 남긴다(연결은 유지). | 해석 | Synapse §4. 서버가 64KB 초과를 끊으므로 실제로는 오지 않음 |
| 3.4d | 텍스트는 UTF-8 JSON으로 읽는다(키는 소문자). `type`이 `client.registered`면 3.1 상태 전환, `error`면 `data.code`·`data.message`를 경고 로그. 그 밖의 `type`은 로그 후 무시. | 확정 | Synapse §4.1, §5, §6 |
| 3.4e | 바이너리는 §4로 넘긴다. | 확정 | `[Vishamos-Data-Route]` |
| 3.4f | 수신·해석은 메시지마다 새 배열을 만들지 않는다(버퍼 재사용). 초당 약 90개(Body 30 + Face 60)가 들어온다. | AI 제안 | 메시지마다 할당하면 GC가 쌓여 프레임이 튈 수 있음 |
| 3.4g | 메시지 내용을 매번 로그로 쓰지 않는다. | AI 제안 | 옛 코드는 수신마다 로그를 남겼음. 초당 90줄이면 로그 파일과 성능에 부담 |

### 3.5 종료 (`[Vishamos-Net-Receive]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.5a | 앱을 끄거나 에디터 플레이를 멈추면 재접속을 멈추고, 연결을 정상 종료(1000)한 뒤 수신 대기를 취소한다. | 확정 | `[Vishamos-Net-Receive]` |
| 3.5b | 정상 종료는 최대 1초만 기다리고, 넘으면 강제로 끊는다. | AI 제안 | 서버가 응답하지 않을 때 종료가 멈추지 않게 함 |
| 3.5c | 플레이를 멈춘 뒤 비동기 작업이 남아 로그·예외를 내지 않아야 한다. | AI 제안 | 옛 코드는 플레이 종료 후에도 수신 루프가 살아 있었음 |

## 4. 데이터 (`[Vishamos-Data-…]`)

### 4.1 구분 (`[Vishamos-Data-Route]`)

| from | 바이트 2 (종류) | 바이트 3 (버전) | 길이 | 처리 | 근거 |
|---|---|---|---|---|---|
| 31 Body | 31 | 1 | 1,080 | §4.3 | Body §2, §5 |
| 22 Face iOS | `0x16` | 1 | 222 | §4.4 | Face §2, §3 |
| 그 밖 (21 Face Android 옛 형식 `0x15` 포함) | | | | 버림 | `[Vishamos-Data-Route]` |

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 4.1a | 바이트 0(`to`)이 11이 아니면 버린다. | 해석 | Synapse §4.2. 서버가 11로만 보내므로 실제로는 오지 않음 |
| 4.1b | `from`·종류·버전·길이가 위 표와 **모두** 맞을 때만 해석한다. 하나라도 다르면 버린다. | 확정 | `[Vishamos-Data-Route]`, Body §5, Face §3, §6 |
| 4.1c | 버린 메시지는 `(from, 종류, 버전, 길이)` 조합마다 처음 한 번만 경고 로그를 남긴다. | AI 제안 | 버전이 다른 송신기를 켜 두면 초당 수십 번 버리므로 로그가 넘치지 않게 함 |
| 4.1d | 숫자는 리틀 엔디언으로 읽는다. | 확정 | Synapse §4.2 |

### 4.2 보관 (`[Vishamos-Data-Latest]`, `[Vishamos-Data-Timeout]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 4.2a | 송신원(Body, Face)마다 가장 최근에 해석한 프레임 하나와 받은 시각을 보관한다. 다른 스크립트는 자기 `Update`에서 최신 프레임을 읽는다. | 확정 | `[Vishamos-Data-Latest]` |
| 4.2b | 받은 시각은 `Time.realtimeSinceStartup` 기준이다. | AI 제안 | `Time.time`은 일시정지·timeScale 영향을 받음 |
| 4.2c | 송신원 수신 상태: 없음(한 번도 받지 않음) / 수신 중 / 신호 없음. 마지막 프레임 이후 1초가 지나면 신호 없음. | 확정 | `[Vishamos-Data-Timeout]`, Body §5 예시값 |
| 4.2d | Synapse 연결이 끊기면 모든 송신원을 바로 신호 없음으로 바꾼다. 마지막 프레임 값은 지우지 않는다. | 해석 | 끊긴 동안 1초를 기다릴 이유가 없음. 값은 다음 단계(놓쳤을 때 동작)에서 쓸 수 있게 남김 |
| 4.2e | 신호 없음 판정 시간(1초)은 코드 상수로 둔다(설정 파일에 넣지 않음). | AI 제안 | 바꿀 일이 생기면 그때 설정으로 옮김 |
| 4.2f | 같은 종류의 송신기가 여러 대 보내는 경우는 따로 처리하지 않는다(운영 규칙: 하나만 켠다). | 확정(사용자 답변) | `[Vishamos-Data-Duplicate]` |
| 4.2g | 송신원마다 "재시작" 신호(또는 카운터)를 둔다. `seq`가 이전보다 작아지면 올린다. 다음 단계(스무딩 등)가 이 신호로 상태를 초기화한다. | 해석 | `[Vishamos-Data-Body]` "이전 상태를 초기화". 1단계에는 초기화할 상태가 없으므로 신호만 제공 |
| 4.2h | 2대가 동시에 보내면 4.2g 재시작 신호가 계속 올라간다. 원인을 찾을 때 이 현상을 단서로 쓴다(따로 감지하지 않음). | 해석 | `[Vishamos-Data-Duplicate]` "따로 처리하지 않는다"와 4.2g의 부작용 |

## 5. 확인 방법 (사용자 테스트)

명세의 동작이 곧 확인 기준이다. 사용자가 코드를 쓴 뒤 아래로 확인한다.

| 확인 | 기대 결과 | 명세 |
|---|---|---|
| 설정 파일 없이 실행 | 파일이 기본값으로 생기고, 에러 로그 1줄, 접속 시도 없음 | 2.4 |
| 서버를 끈 채 실행 | 접속 중 → 연결 안 됨이 약 3초(+최대 5초)마다 반복, 예외 없음 | 3.2e, 3.3a |
| 서버를 켬 | 3초 안에 연결됨. 로그에 `등록 대기 → 연결됨` | 3.2b, 3.1a |
| 서버를 끔·다시 켬 | 연결 안 됨 → 재접속 → 연결됨. 재접속 루프가 하나뿐(로그 간격이 일정) | 3.3a, 3.3b |
| 연결된 채 5분 이상 둠 | 서버가 끊지 않음(ping 자동 응답) | 3.4a |
| Body 트래커 실행 | Body 수신 중, 초당 약 30프레임, 로그 넘침 없음 | 4.2, 3.4g |
| Body 트래커 재시작 | 재시작 신호 1회 | 4.3e |
| Body 트래커 종료 | 1초 뒤 Body 신호 없음 | 4.2c |
| Face 앱 실행·종료 | Face 수신 중 / 1초 뒤 신호 없음. Face 재접속 시 재시작 신호 1회 | 4.2c, 4.4d |
| 에디터 플레이 중지 | 이후 Synapse 관련 로그·예외 없음, 서버 로그에 정상 종료 | 3.5 |
| Profiler에서 수신 중 GC Alloc | 메시지마다 할당이 없음 | 3.4f |
