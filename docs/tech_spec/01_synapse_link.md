## 3. 연결 (`[Vishamos-Net-…]`)

### 3.1 연결 상태 (`[Vishamos-Net-Status]`)

| 상태 | 뜻 | 다음 상태 |
|---|---|---|
| 연결 안 됨 | 시작 직후, 끊긴 뒤 재접속 대기 | 재접속 시각이 되면 → 접속 중 |
| 접속 중 | WebSocket 접속 시도 | 성공 → 등록 대기 / 실패 → 연결 안 됨 |
| 등록 대기 | 접속 성공, `client.register`를 보내고 응답 대기 | `client.registered` 수신 → 연결됨 / 끊김 → 연결 안 됨 |
| 연결됨 | 데이터 수신 | 끊김 → 연결 안 됨 |

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.1a | 상태는 위 4개로 닫는다. 상태가 바뀔 때마다 로그를 한 줄 남긴다(`이전 → 다음`, 끊김이면 종료 코드·이유). | 확정(사용자 답변) | `[Vishamos-Net-Status]`. 표시는 로그만, 화면 표시는 VishasController |
| 3.1b | 상태를 화면에 표시하지 않는다. | 확정(사용자 답변) | `[Vishamos-Net-Status]`, CLAUDE.md 안전 규칙 1 |
| 3.1c | 다른 스크립트가 현재 상태를 읽을 수 있게 한다(나중에 Controller로 보낼 때 씀). | AI 제안 | 상태를 바깥에 알릴 경로가 하나는 있어야 함 |

### 3.2 접속·등록 (`[Vishamos-Net-Connect]`, `[Vishamos-Net-Register]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.2a | 실행하면 자동으로 접속한다. 주소: `ws://<ServerHost>:<ServerPort>` | 확정 | `[Vishamos-Net-Connect]`, Synapse §1 |
| 3.2b | 접속 직후 기다리지 않고 텍스트로 `{"to":0,"from":11,"type":"client.register","data":""}`를 보낸다. 서버가 먼저 보내는 메시지는 없다(옛 `[0,0]` 대기 제거). | 확정 | `[Vishamos-Net-Register]`, Synapse §3, §9 |
| 3.2c | `client.registered`를 받기 전에 온 바이너리는 버린다. | 해석 | `[Vishamos-Net-Register]` "받은 뒤부터 처리". 서버도 등록 전에는 전달하지 않으므로 실제로는 오지 않음 |
| 3.2d | 등록 응답을 기다리는 클라이언트 쪽 시간 제한은 두지 않는다. 등록이 안 되면 서버가 30초 뒤 끊고(1008), 3.3에 따라 다시 접속한다. | 해석 | Synapse §3. 서버 시간 제한으로 충분 |
| 3.2e | 접속 시도 자체의 시간 제한: 5초 | AI 제안 | 서버 PC가 꺼져 있으면 `ConnectAsync`가 OS 기본 시간(수십 초)까지 걸려 재접속 3초 간격이 의미 없어짐 |

### 3.3 재접속 (`[Vishamos-Net-Reconnect]`)

|---|---|---|---|

| 3.3b | 재접속 시도는 한 번에 하나만 돈다(중복 루프 금지). | 확정 | `[Vishamos-Net-Reconnect]`. 옛 코드는 코루틴이 2개 생겨 연결이 10초마다 끊겼음(§8) |

### 3.4 수신 (`[Vishamos-Net-Receive]`)

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.4a | 연결 중에는 수신 대기(`ReceiveAsync`)를 항상 걸어 둔다. `ClientWebSocket`은 수신 대기 중일 때만 서버 ping에 pong을 자동으로 보낸다. | 확정 | `[Vishamos-Net-Receive]`, Synapse §7 |
| 3.4b | 한 메시지는 `EndOfMessage`가 올 때까지 이어 붙여 하나로 처리한다. | 확정 | `[Vishamos-Net-Receive]` |
| 3.4c | 이어 붙인 길이가 64KB를 넘으면 그 메시지를 버리고 경고 로그를 남긴다(연결은 유지). | 해석 | Synapse §4. 서버가 64KB 초과를 끊으므로 실제로는 오지 않음 |
| 3.4d | 텍스트는 UTF-8 JSON으로 읽는다(키는 소문자). `type`이 `client.registered`면 3.1 상태 전환, `error`면 `data.code`·`data.message`를 경고 로그. 그 밖의 `type`은 로그 후 무시. | 확정 | Synapse §4.1, §5, §6 |
| 3.4e | 바이너리는 §4로 넘긴다. | 확정 | `[Vishamos-Data-Route]` |
| 3.4f | 수신·해석은 메시지마다 새 배열을 만들지 않는다(버퍼 재사용). 초당 약 90개(Body 30 + Face 60)가 들어온다. | AI 제안 | 메시지마다 할당하면 GC가 쌓여 프레임이 튈 수 있음 |
| 3.4g | 메시지 내용을 매번 로그로 쓰지 않는다. | AI 제안 | 옛 코드는 수신마다 로그를 남겼음. 초당 90줄이면 로그 파일과 성능에 부담 |

## 5. 확인 방법 (사용자 테스트)

명세의 동작이 곧 확인 기준이다. 사용자가 코드를 쓴 뒤 아래로 확인한다.

|---|---|---|
| 설정 파일 없이 실행 | 파일이 기본값으로 생기고, 에러 로그 1줄, 접속 시도 없음 | 2.4 |
| 서버를 끈 채 실행 | 접속 중 → 연결 안 됨이 약 3초(+최대 5초)마다 반복, 예외 없음 | 3.2e, 3.3a |
| 서버를 켬 | 3초 안에 연결됨. 로그에 `등록 대기 → 연결됨` | 3.2b, 3.1a |
| 서버를 끔·다시 켬 | 연결 안 됨 → 재접속 → 연결됨. 재접속 루프가 하나뿐(로그 간격이 일정) | 3.3a, 3.3b |
