# 기획 비교·반영 절차

## 원칙
- 기획서 원본은 노션 `VishaSTD / Vishamos`와 하위 페이지. **사용자가 쓰고 Claude는 읽기만 한다.**
- 노션은 기획 수준(방향)만 담는다. 세부 값·동작은 대화로 사용자가 정하고, plan_review에 "결정됨(날짜, 사용자)"으로 기록한다. 명세 근거는 노션 태그와 이 결정 둘 다다.
- 비교용으로 읽는 것: VishaSynapse·VishasBody·VishaFace_IOS의 `docs/protocol/README.md`(CLAUDE.md 지도).
- **답을 받기 전에는 추측으로 채우지 않는다.**
- 범위: Vishamos가 알아야 동작하는 것만.

## 1. 비교 (worklist → 노션)
- worklist 항목마다 구현에 필요한 것(동작, 값, 실패·끊김 처리, 빈도·크기, 방송 화면 노출 여부)을 뽑는다.
- 노션에서 해당 태그(`[Vishamos-<영역>-<이름>]`)를 찾아 있음 / 부족 / 없음으로 나눈다.
- 부족·없음 항목은 나눠서 알린다: 기획 방향이 없으면 "노션에 적을 것", 세부 값·동작이면 대화로 바로 묻는다. 선택지가 있으면 추천안과 이유 한 줄을 붙인다. 노션에는 쓰지 않는다.

## 2. 사용자가 반영했다고 할 때
- 노션을 다시 읽고 마지막 수정 시각을 기록한다.
- 항목마다 판단한다: 충분 / 부족(무엇이 빠졌는지) / 외부 규약·현재 코드와 충돌(근거: `저장소 §절`, 파일:줄).
- 태그가 없거나 중복이면 함께 알린다.

## 3. 명세로 옮기기 (노션 기획과 대화 결정이 갖춰졌을 때)
- `docs/tech_spec/NN_<주제>.md`. 상단에 상태, 근거 노션 페이지와 수정 시각, 참조한 외부 규약의 판, "항목 구분" 정의.
- 항목 구분: `확정` 노션·외부 규약에 명확한 것 / `확정(사용자 답변)` 대화로 정한 것 / `해석` 모호한 부분을 보충한 것(승인 필요) / `보류` 해당 작업 때 정함 / `확인 필요` 결정이 필요한 것 / `AI 제안` 노션에 없는 것(승인 필요).
- `근거` 열에는 기획 태그, 외부 규약 절, 또는 대화 결정(날짜, plan_review 번호)을 적는다. `해석`·`AI 제안` 행에는 이유를 한 문장 덧붙인다.
- 명세는 "무엇을"(동작·값·실패 처리)까지 쓰고 클래스 구조는 정하지 않는다(코드는 사용자가 쓴다).
- 명세 끝에 "구현 현황" 표(항목, 상태, 커밋)를 둔다.

## 4. worklist
- 항목 형식: `- [ ] <번호> <내용> — 기획: [태그] / 명세: <문서 번호> §<절>`
